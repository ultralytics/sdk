# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, etc.) when working with code in this repository. CLAUDE.md is a symlink to this file.

`ultralytics/sdk` publishes `ultralytics-platform` (PyPI, AGPL-3.0, Python >=3.11, one runtime dependency: `httpx`): typed sync/async Python clients for the Ultralytics Platform API plus the unified `ul` CLI. Almost everything under `sdk/python/` is generated by the `ultralytics/openapi` generator from the pinned contract snapshot `openapi.json`; the only hand-written Python is root `cli.py`, root `auth.py`, and `tests/`. Downstream, the `ultralytics` package declares a dependency on `ultralytics-platform`, re-exports `Platform`/`AsyncPlatform`/`APIError`/`APIConnectionError`, and implements `yolo login` with `Platform(api_key=..., base_url=..., timeout=...).account.summary()` — treat the public client surface as a compatibility boundary.

## Core Principles (CRITICAL)

**Less is more. The simplest solution is the best solution.** The action hierarchy for every change: **Delete > Replace > Add**.

1. **Solve at the owner**: Put behavior in the code path that owns or observes it. For fixes, never guard a symptom with a staleness check, initialization flag, skip-first-call branch, or `try/except` around broken logic; relocate the trigger and delete the wrong path. For features, extend the existing owner rather than creating a parallel abstraction.
2. **Search and reuse first**: Search the whole repository before creating a feature, component, helper, workflow, or utility. Reuse or adapt what exists, consolidate in-scope duplication in the shared owner, and delete duplicate paths. Three similar lines beat a helper nobody else calls.
3. **Delete and modify existing code before creating new code**: Bugfixes are net-negative by default unless deletion and relocation are demonstrably impossible. A new file must first prove it cannot fit cleanly in an existing owner.
4. **Keep scope minimal**: Implement only the simplest complete solution. Avoid impossible-state handling, speculative flags, compatibility shims, policy scaffolding, and unrelated cleanup. Tests are out of scope by default — rely on existing coverage and focused validation; only an uncovered, high-risk regression path justifies minimal new test code.
5. **Ship zero-regression, production-ready changes**: Understand what you remove instead of retaining broken code as insurance. Remove unused imports, functions, types, files, and comments; run relevant cleanup checks; and thoroughly debug and validate the changed owner. Do not break existing features or workflows unless the PR intentionally removes them with evidence.

**Review gate:** for every addition, the reviewer decides whether deleting or changing existing code would have fixed the problem instead — if it would, that is a blocking finding. A missing or thin PR description is never itself a finding.

NEVER push to `main`. NEVER force push. Always start work in a new git worktree (`git worktree add`) on a feature branch and open a PR — never edit the primary checkout directly, it may hold in-flight work.

## PR Workflow

After opening a PR:

1. Wait for the automated PR review and auto-format commit from Ultralytics Actions (`format.yml`), then pull and address every finding.
2. Review the full diff in-session against the Core Principles, performance, and the review gate above, then batch the fixes into one commit and push. After each round of bot or human commits, pull and resume the same reviewer on `<last-reviewed-sha>..HEAD` plus anything that delta could have invalidated. Repeat until the local head matches the live head.
3. Hand off or merge only on a clean final pass: one cold full-diff review returning LGTM with no findings, on a head that is still live at merge time.
4. Never fight other commits: Ultralytics Actions pushes auto-format and header commits, and multiple users may work on the same PR. `git pull --rebase` before pushing; never reset or revert commits you did not author.
5. After the PR merges, clean up: remove local worktrees and branches for it, then `git checkout main && git pull`.

Root `cli.py` uses package-relative imports (`from . import ...`) and is not a runnable script; always exercise the installed `ultralytics_platform.cli` module.

CI checks Python 3.11 and 3.14 on Ubuntu. It verifies the versioned Platform contract against `openapi.sha256`, regenerates the Python output from the `main` branch of `ultralytics/openapi`, fails on generated drift, and then runs the Python checks above plus a Git subdirectory install (`uv pip install "git+file://$GITHUB_WORKSPACE@<sha>#subdirectory=sdk/python"`). The `Live` job ("Full API lifecycle") runs on every `main` ref build (pushes and the daily cron) and on manual dispatch — never on pull requests. It downloads the upstream contract and regenerates the SDK; only `main` runs with detected changes open and merge the contract-update PR on green checks without human involvement (a manual run on another ref skips that step), and every Live run ends with the production canary in `tests/live_readonly.py`, so a canary failure never blocks the SDK from tracking the contract. A canary failure does fail the CI run; `publish.yml` runs on every CI completion but its `check` job publishes only when that CI run was push-triggered on `main` and succeeded, so the failure blocks automatic PyPI publication until a later push to `main` passes CI (scheduled and manual CI successes never publish; a manual `pypi` dispatch is the recovery path). New endpoints do not need canary coverage; add it only when live behavior is worth guarding.

## Where to look

Start by comparing the affected operation in `openapi.json` with its generated method: wrong contract content belongs to the API owner, a correct contract translated wrongly belongs to the generator, and CLI discovery/parsing/help presentation belongs to root `cli.py`.

- CLI parsing, implicit verbs, help output, exit codes, owner inference → root `cli.py`, then regenerate so `sdk/python/src/ultralytics_platform/cli.py` matches; the drift gate fails if you edit the copy. Cover behavior in `tests/test_cli.py` (real subprocess + loopback server), not by mocking `dispatch`.
- Saved-key discovery (`yolo login` settings, `YOLO_CONFIG_DIR`) → root `auth.py`, regenerate. Precedence between explicit key, env var, and provider is generated code in `_client.py` (`_resolve_api_key`) — change it in `ultralytics/openapi`.
- Transport bugs (retries, timeouts, header injection, response decoding, query/path serialization) → `_client.py` is generated (the generator's `lib/generators/python.ts`, `clientSource`); fix there, let the Live sync land it here, and set `python.version` if it must publish now (see Releases).
- Wrong SDK method or argument name, type, `Literal` choices, docstring, or CLI help text → argument docs and choices come straight from the OpenAPI schema and method names from `x-sdk-method`/path rules, all produced in the `portal` repo's OpenAPI generation (`scripts/generate-openapi.ts`, route `contract.ts` files with `sdkMethod`) and delivered here by the Live job. Do not patch `resources/*.py` or `types.py`. If the contract is right and the Python is wrong, it is a generator bug.
- New API endpoint → nothing to write here. The Live job regenerates and `tests/test_python_sdk.py::test_all_operations_serialize` requires every contract operation to be callable on both clients. Add a canary scenario in `tests/live_readonly.py` only when live behavior is worth guarding (`expected_error(...)` for operations that cannot safely succeed).
- Package metadata (classifiers, `requires-python`, description, keywords, PyPI README) → `openapi.config.json` `python.*` and `README.python.md`, then regenerate; `sdk/python/pyproject.toml` and `sdk/python/README.md` are outputs.
- Contract refresh by hand → replace `openapi.json`, `sha256sum openapi.json > openapi.sha256`, regenerate, check the version rule below.
- Release or publish problems → `publish.yml` `check` job and the version arithmetic in `ci.yml` `Live` "Sync live OpenAPI contract" / "Apply generated changes".
- Canary failures → `response_validator()` (status/schema rejection), `exercise_api()` (the failing scenario), `validate_sdk()` (aggregated schema errors, cleanup failures, classification drift) in `tests/live_readonly.py`.

## Architecture

- The API/docs/SDK repository chain always follows `main`: cross-repository `ultralytics/openapi` checkouts must use `ref: main` and must never pin a commit SHA or tag.

This repository contains generated SDKs for Ultralytics products. `openapi.config.json` defines the consumer configuration; `openapi.json` and `openapi.sha256` pin the contract. All of `sdk/python/` is generated, committed, and drift-checked; never edit it manually. Maintain CLI behavior in root `cli.py` and shared credentials in `auth.py`. The generator copies these sources into the package, emits multipart binary-field metadata in `_cli_metadata.py`, and registers `ul`; `cli.py` owns the launcher. The CLI discovers operations, types, and help from SDK signatures and docstrings. After changing sources, configuration, or contract, regenerate with an `ultralytics/openapi` main checkout at `.generator/` and copy `.generator/generated/python/` to `sdk/python/`. `tests/` owns consumer checks; `format.yml` applies Ultralytics Actions, `ci.yml` owns regeneration and package validation, and `publish.yml` owns releases and PyPI publishing.

Paths below are relative to the repository root; `pkg/` abbreviates `sdk/python/src/ultralytics_platform/`. Facts about the generator itself describe `ultralytics/openapi` `main` (`lib/config.ts`, `lib/openapi.ts`, `lib/generators/python.ts`, `scripts/{sync,generate,headers}.ts`), which is not in this checkout; verify them against the generated output here.

### Generator inputs and outputs

Generated output is a function of four things: `openapi.json`, `openapi.config.json`, the configured source files, and the generator revision on `main`. From `openapi.config.json`: `source` (`openapi.json`, copied to `.generator/public/openapi.json` by `bun run sync`), `upstream` (used only by the Live job), `apiKey.environment` (`ULTRALYTICS_API_KEY`), `header` (license header stamped onto generated `.py`/`.toml` files), `license`, and `python.*`: `client` (`Platform`), `package` (`ultralytics_platform`), `project` (`ultralytics-platform`), `requiresPython`, `classifiers`, `keywords`, `description`, `authors`/`maintainers`, `readme` (`README.python.md`, copied verbatim to `sdk/python/README.md`), `authProvider` (`auth.py` → `pkg/_auth.py`), `cli` (`command: "ul"`, `source: "cli.py"` → `pkg/cli.py`, `pkg/_cli_metadata.py`, and `[project.scripts] ul = "ultralytics_platform.cli:main"`), and optional `version` (package version; when absent the contract's `info.version` is used).

### Generated package (`pkg/`)

- `__init__.py` exports exactly `NOT_GIVEN`, `NotGiven`, `APIConnectionError`, `APIError`, `AsyncPlatform`, `Platform`.
- `client.py` / `async_client.py`: `Platform(*, api_key=None, base_url="https://platform.ultralytics.com", timeout=60.0, max_retries=2, http_client=None)` resolves the key with `_resolve_api_key` and attaches one resource object per contract tag as attributes (`account`, `billing`, `datasets`, `deployments`, `explore`, `images`, `storage_integrations`, `models`, `exports`, `projects`, `training`, `lifecycle`, `upload`). `timeout=` only configures a client the constructor creates; a supplied `http_client=` keeps its own timeout and is closed by `Platform.close()` / the context manager. `ULTRALYTICS_PLATFORM_URL` is read by the CLI only — Python callers pass `base_url=`.
- `_client.py`: `_resolve_api_key(api_key)` — explicit value (even `""`, which disables auth) → non-empty `ULTRALYTICS_API_KEY` → `get_api_key()` from `_auth.py`. `SyncAPIClient.request` / `AsyncAPIClient.request` build the URL from `base_url` (plus a per-operation `server` override), add the header from the operation's `auth=("Authorization", "Bearer ")` tuple only when a key is set, and serialize: JSON bodies omit fields holding `NOT_GIVEN` but send explicit `None` as `null` (`_json_value`); query parameters, generated headers, and cookies omit both `None` and `NOT_GIVEN` (`_query_parameter`, `_without_none`); form bodies omit `NOT_GIVEN`, and nested dicts are JSON-encoded as a single part for multipart but flattened into individual fields for URL-encoded forms (`_form_data`). Decoding: 204 or empty body → `None`, `application/json`/`+json` → parsed JSON, `text/*` (or `text=True`) → `str`, else `bytes`. Retries: GET/HEAD/OPTIONS retry connection errors and HTTP 408/409/429/5xx; any other method retries only HTTP 429 and only when it carried a JSON body (multipart `predict` is never retried); `max_retries=2` means up to three attempts; delay uses a numeric `Retry-After` (capped 60s; an HTTP-date value is ignored) else `0.5 * 2**attempt` capped at 8s. Errors: `APIError(status_code, body, request_id)` with a `.json` property, `APIConnectionError`.
- `resources/<tag>.py`: one `<Tag>` and one `Async<Tag>` class per contract tag, one method per operation. Path parameters are positional-or-keyword, API arguments are keyword-only with optional ones defaulting to `NOT_GIVEN`, and every method also takes `timeout=None` and `extra_headers=None` (positional-or-keyword on methods without other keyword-only arguments, e.g. `account.summary`, `datasets.retrieve` — the CLI drops these two names before classifying parameters). Python names are snake_case while wire names stay camelCase: `training.start(model_id=..., train_args=...)` sends `modelId`/`trainArgs`; `models.clone(owner, project, model, *, project_body=..., owner_body=..., model_body=...)` separates source path identifiers from destination JSON fields. Whole-object bodies are `body: dict[str, Any]` (e.g. `upload.signed_url`, `images.update`, `deployments.update`, both `predict`s) and keep wire spelling. Return annotations are aliases in `types.py` named `<PascalTag><PascalMethod>Response` — `TypedDict`s, unions of variants (`DatasetsExportResponse`), or plain typed dicts (`TrainingGpuAvailabilityResponse`); methods `cast` the decoded JSON, so there is no runtime response validation. `models.predict` and `deployments.predict` are the only multipart operations: `body["file"]` must be an open binary file object (the SDK never opens a path string, even though the contract's embedded `x-codeSamples` example passes `"path/to/file"`); other `body` keys become form fields.
- `_cli_metadata.py`: `MULTIPART_FILES = {"deployments.predict": ["file"], "models.predict": ["file"]}`, computed from `multipart/form-data` bodies whose properties have `format: binary`.

### Naming rules

Resource = snake_case of the operation's first tag (`Storage Integrations` → `storage_integrations`). Method = the contract's `x-sdk-method` override when present (13 operations use it, e.g. `merge_classes`, `adopt_images`, `selected_images`, `find_similar_images`), else the static path leaf after the resource segment (`/api/datasets/{owner}/{dataset}/class-stats` → `class_stats`), else `retrieve`/`list` for GET and `create`/`update`/`delete` for POST/PATCH-PUT/DELETE, with collision fallbacks (`<leaf>_<parent>`, `<verb>_<leaf>`, numeric suffix). Python reserved words gain a trailing underscore (`from_`). Overrides originate as `sdkMethod` in the `portal` repo's route `contract.ts` files, so a bad SDK method name is fixed upstream, never here.

### CLI (`cli.py`, copied to `pkg/cli.py`; console script `ul`)

`main(argv)` → no args / `help` prints usage; `version` prints `ultralytics-platform` and `ultralytics` versions; `cloud ...` → `dispatch()`; every other first token (`login`, `logout`, `train`, `val`, `predict`, `export`, `track`, `benchmark`, `settings`, `checks`, `cfg`, `copy-cfg`, `solutions`, ...) requires an importable `ultralytics`, mutates `sys.argv[:]` in place to `["yolo", *args]` before importing `ultralytics.cfg.entrypoint`, and restores it in `finally` (YOLO aliases that list as `ARGV` and keys behavior off the executable name, so keep the slice assignment). `ul login API_KEY` is therefore `yolo login`, which validates via `Platform(...).account.summary()` and writes `api_key` into the shared `settings.json`.

`dispatch()` builds `Platform(base_url=os.getenv("ULTRALYTICS_PLATFORM_URL", "https://platform.ultralytics.com"))`, discovers resources from `vars(client)` and operations from public bound methods (names hyphenated: `storage-integrations`, `usage-summary`; argument keys keep the Python names), then: `assignments()` parses `key=value` tokens (rejects `--key value`; merges `name` `=value`; duplicates error), `defaults()` derives implicit verbs (bare resource → `list`; `retrieve` when its extra path identifiers are supplied; resources without `list` print help, or exit 2 when arguments were supplied without an operation), `describe()` turns the SDK signature + `get_type_hints` into `{types, choices, required, path}` descriptors via `kinds()` (skipping `timeout`/`extra_headers`), `parse()` coerces text to JSON kinds (`@file` / `@-` stdin for object/array/any-typed args, one stdin use max, `None`/`null` only for nullable, rejects NaN/Infinity, validates `Literal` choices, treats a missing path `owner` as optional), `open_inputs()` opens `@path` for `BinaryIO` args and for `MULTIPART_FILES` fields inside `body`, the owner is inferred with one `client.account.summary()["username"]` call when `owner=` is absent (project identifiers and `owner_body` are never inferred), and `output()` prints JSON (indent 2), text, or raw bytes. The CLI validates only top-level kinds, required arguments, choices, and finite numbers; nested request schemas are validated by the API. Each invocation performs exactly one SDK operation (plus the owner lookup): no pagination, polling, artifact download, or cancellation on interrupt. Help (`help`, `--help`, `-h` as a bare token) prints the first docstring line per operation, or the full docstring minus `timeout`/`extra_headers` for one operation. Exit codes in `main()`: `APIError` → 1 (prints `API request failed (HTTP <status>): <body.error>` only, never the raw body), `APIConnectionError` → 1, `ValueError`/`OSError` → 2, `KeyboardInterrupt` → 130.

### Credentials (`auth.py`, copied to `pkg/_auth.py`)

`get_api_key()` mirrors the `ultralytics` settings-directory logic without importing it: `YOLO_CONFIG_DIR/Ultralytics`, else Linux `$XDG_CONFIG_HOME` or `~/.config/Ultralytics`, Windows `~/AppData/Roaming/Ultralytics`, macOS `~/Library/Application Support/Ultralytics`; it then selects the first of that directory, `/tmp/Ultralytics`, and `./Ultralytics` that exists or whose parent is writable, and reads `settings["api_key"]` from `settings.json` there. Missing, unreadable, or malformed settings in the selected location return no key without searching elsewhere, and the `""` written by `yolo logout` yields no auth rather than a key from another location.

### Contract snapshot (`openapi.json`)

~0.9 MB, OpenAPI 3.2.0, `info.version` = `0.1.39`, 60 paths / 86 operations / 13 tags, `servers[0]` = production. Declared response content is always `application/json`; request bodies are JSON except the two multipart `predict` operations. 21 operations declare optional auth (`security: [{}, {BearerAuth}]`) but the SDK still sends the header whenever a key resolves. `x-codeSamples` hold the Python examples embedded in the contract.

### Releases

The package version is `python.version` in `openapi.config.json` when set, else `openapi.json` `info.version`; both must be `MAJOR.MINOR.PATCH`. The Live job takes `max(contract version, current pyproject version)`: when the contract is newer it removes `python.version` so the SDK adopts it; when freshly generated output differs from the committed `sdk/python` at an unchanged version (a generator change landing through the daily sync), it bumps the patch and writes `python.version`. The trap: if you commit a `cli.py`/`auth.py`/README/config change together with its regenerated output at the existing version, Live sees no difference and never bumps, so nothing publishes. For an SDK-only release set `python.version` to the next patch and regenerate in the same PR (PR #61 did exactly this: `openapi.config.json`, `sdk/python/pyproject.toml`, and the regenerated `_client.py`). `publish.yml` releases whenever a CI push run on `main` succeeds and `main`'s version is greater than PyPI's.

## Gotchas

- `tests/live_readonly.py` is not read-only and is not collected by pytest. It needs `ULTRALYTICS_API_KEY`, runs against production, creates and deletes `sdk-ci-<timestamp>` projects/datasets/models, uploads `coco32.zip` from `ultralytics/assets`, and paces requests at 0.75s. Its response hook validates successful responses that declare a JSON schema against `openapi.json`, rejects 401/5xx and undocumented statuses, and checks the exact error message of any 403 against `EXPECTED_FORBIDDEN`. Operations that cannot succeed on the canary account (training start, export, deployment create, ...) are wrapped in `expected_error(...)` and must fail; the final gate fails when the set of error-only operations drifts from those classifications. It exercises explicit scenarios, not every operation (e.g. `models.find_similar_training_images` is not called). Run it only deliberately.
- `ULTRALYTICS_API_KEY=""` (empty) does not disable auth — `_resolve_api_key` treats an empty environment value as unset and falls through to the saved `yolo login` key (that is how `tests/test_cli.py` forces the settings path). Only an explicit `Platform(api_key="")` disables the header.
- `tests/test_cli.py` runs the CLI as `sys.executable -m ultralytics_platform.cli` with `YOLO_CONFIG_DIR=<tmp>` and `ULTRALYTICS_PLATFORM_URL=http://127.0.0.1:<port>`; without an installed package it fails with `No module named ultralytics_platform`, and it asserts that error output never echoes upstream bodies or private argument values.
- Run the `diff --recursive` drift check on a clean tree: `pytest`, `compileall`, and `uv build` leave `__pycache__/` and `sdk/python/dist/` behind, which the recursive diff reports even though git ignores them.
- `ul login`/`ul logout` and all local commands need `ultralytics` installed in the same environment; `ul cloud ...` does not.
- Shell quoting: JSON arguments need single quotes (`'train_args={"epochs":1}'`), `@-` may be used by at most one argument per invocation, and binary fields must be `@path` (never stdin) even when nested inside a multipart `body` JSON.
- Editing anything under `sdk/python/` is wasted work: `bun run generate` rewrites `.generator/generated/python` (including `ruff format` and header insertion) and the `rsync --delete` copy replaces the committed tree; CI's Test job reports the difference instead of fixing it.
- `.generator/` is gitignored but `.generator/generated/` and `.generator/public/` are written during regeneration; delete the directory if a stale clone causes confusing diffs.
- `format.yml` will not reformat Python or Markdown for you here (`python: false`, `prettier: false`); run the pinned `uvx ruff@0.16.2 format --line-length 120` on `cli.py`, `auth.py`, and `tests/` yourself before pushing.

## Tests

- `tests/test_python_sdk.py`: `httpx.MockTransport` only. `test_priority_resource_requests` pins exact method/path/body for the README examples; `test_async_resource_tree` checks the absolute production URL; `test_all_operations_serialize` walks every public method on `Platform` and `AsyncPlatform` (`operations()`), fills required arguments with synthetic values by annotation (`required_arguments()`), and asserts the sorted `(METHOD, path)` set equals every operation in `openapi.json` — a coverage check for method/path pairs, not full query/body/response-schema validation; `test_api_error_details` checks `APIError.status_code`, `.body`, `.request_id`.
- `tests/test_cli.py`: one test, `test_cli_wire_and_auth`, drives the installed CLI through real subprocesses against a `ThreadingHTTPServer` on `127.0.0.1` that records method, path, headers, and body: saved-settings vs environment key precedence, implicit `list`/`retrieve`, help variants, exit code 2 for local input errors (unknown argument, bare non-boolean, non-finite numbers, duplicate stdin), exit code 1 with sanitized messages for HTTP 401/422, `False`/`0`/`null`/`"None"` value semantics, `@file` and `@-` JSON inputs, and multipart `@path` uploads.
- `tests/live_readonly.py`: the production canary described in Gotchas. `validate_sdk()` installs the `pace_request` and `response_validator` hooks on a plain `httpx.Client`, `exercise_api()` runs the lifecycle scenarios and registers cleanup callbacks (executed in reverse order; `cleanup_resource`/`cleanup_created` tolerate 404s), and the upload scenario is the reference flow: `upload.signed_url` → direct HTTP `PUT` to the returned `uploadUrl` with its `headers` → `upload.complete` → `datasets.ingest` → `wait_for_images`. The dataset download and the signed `PUT` are plain `httpx` calls outside the SDK hooks. Requires `jsonschema` and `referencing`.
- No `conftest.py`, no fixtures beyond `tmp_path`, no external network in the pytest suite. CI runs `pytest tests -v` on Python 3.11 and 3.14 after a Git-subdirectory install.

## Conventions

- Ultralytics-owned PyPI packages use `MAJOR.MINOR.PATCH` versions only; no suffixes.
- License headers (`# Ultralytics 🚀 AGPL-3.0 License - https://ultralytics.com/license`) are added automatically by Ultralytics Actions — don't add or revert them manually. Generated files receive the same header from the generator (`header` in `openapi.config.json`).
- Google-style docstrings, `from __future__ import annotations` for modern type hints, line length 120; formatting is checked by `ci.yml` with the pinned `uvx ruff@0.16.2` (`format.yml` runs with `python: false`, so nothing reformats Python on PR branches) and the generator formats its own output.
